# Kord implementation plan

## Scope and delivery approach

Kord will be delivered as a mobile-first React 18 + Vite single-page application with React Router, plain CSS, lucide-react icons, and a Supabase adapter. The application will support the complete learner and administrator journey described in the brief, including the seeded learning content, quiz scoring flow, challenge evidence flow, review rubric, skill progression, and opportunity matching.

Because Supabase project credentials were not supplied in this task, the UI will include a clearly separated demo-data adapter so the preview is usable immediately. When `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` are present, the same repositories switch to Supabase Auth, Postgres, Storage, RLS and RPCs without changing page components. Demo mode will be explicitly labelled in the interface and will never be used as a substitute for the SQL/RLS implementation. The SQL files remain the source of truth for the real deployment.

The admin account requirement will be represented in both modes: `ethoppaofficial@gmail.com` is the demo administrator identity, and the Supabase profile trigger will assign the admin role to that email while all other new users default to learner. The implementation will not expose quiz answers through the learner data path; demo-mode answers will be held inside the quiz repository and the real path will use `submit_quiz`.

## Architecture

- **Presentation:** `src/pages` contains route-level screens; `src/components` contains reusable UI primitives and layout pieces. Pages receive data and actions through hooks and repositories rather than embedding storage logic.
- **State and data:** `src/lib/repositories` provides auth, content, progress, quiz, submission and recommendation interfaces. `src/hooks` owns loading/error state and route-specific orchestration. `src/lib/demo` contains deterministic demo records and localStorage persistence for preview-only mode.
- **Supabase:** `src/lib/supabase.js` creates the browser client only when public environment variables exist. SQL is split into the five ordered files requested by the brief and uses RLS, security-definer functions, triggers and private Storage policies.
- **Navigation:** `src/App.jsx` defines public, protected learner and protected admin routes. `ProtectedRoute` guards authentication and role access. `AppLayout` provides the desktop top bar and mobile bottom navigation; `AdminLayout` adds the admin navigation.
- **Validation and feedback:** Shared form components provide labels and validation messaging. A small toast provider handles successful mutations and recoverable errors. Every route has loading, empty and error branches, with an error boundary around the application shell.
- **Styling:** `src/styles/tokens.css` contains the specified design tokens; component/page styles are colocated in separate CSS files. The CSS uses a restrained responsive layout with CSS grid/flex only where it improves readability, avoiding dense dashboard tables on mobile.
- **Deployment:** Vite builds to `dist`; `vercel.json` rewrites unknown paths to `/index.html`. `public/manus-routes.json` lists all declared routes for Preview tooling. `.env.example` documents the two browser-safe Supabase variables.

## Design direction

Three possible styles were considered: **Editorial learning journal** (0.08): quiet reading surfaces, blue ink accents and clear progress markers; **Civic skills lab** (0.06): structured panels, confident navy framing and practical evidence motifs; **Bright opportunity board** (0.04): energetic cards, stronger color blocking and a marketplace feel.

The chosen direction is **Civic skills lab**.

- **Design movement:** Contemporary civic-tech/productivity interface: trustworthy, structured and human, with a learning-lab sensibility rather than an entertainment-app aesthetic.
- **Core principles:** Evidence over hype; progressive disclosure; calm focus; obvious next actions.
- **Color philosophy:** The supplied blue palette signals trust and forward motion. Navy anchors the brand and high-contrast text, while the pale tint gives activities and recommendation states a quiet workspace feel. Green, amber and red are reserved for status meaning.
- **Layout paradigm:** A left rail/top-bar desktop shell becomes a compact bottom navigation on mobile. Route pages use a wide reading column with an offset evidence or action panel instead of a generic centered card grid.
- **Signature elements:** slim blue progress rails, rubric rows that feel like assessment sheets, and small “evidence” chips for resources/submissions/skill levels.
- **Interaction philosophy:** Every screen answers “where am I, what have I proven, and what should I do next?” Mutations give immediate feedback and never hide status changes.
- **Animation:** Use short, purposeful transitions for progress bars, route content and toasts only. Avoid decorative motion that increases cognitive load or data usage.
- **Typography system:** Inter/system-ui with 44px display headlines, 32px section headings, 24px page headings, 20px card headings, and 14–16px supporting text. Use weight and spacing rather than excessive color to establish hierarchy.
- **Brand essence:** Kord helps emerging professionals turn learning into visible evidence and practical opportunity. Personality: grounded, encouraging, credible.
- **Brand voice:** Headlines are direct and action-oriented; CTAs describe the next proof step. Example lines: “Build evidence, not just intentions.” and “Your next opportunity starts with one completed activity.”
- **Wordmark & logo:** A compact “K” mark formed from two connected blue rails, suggesting a learning path joined to a proof point, paired with the Kord wordmark.
- **Signature brand color:** `#2563eb` as the unmistakable Kord blue, used sparingly for action and progress.

## Data and security decisions

The database schema will use UUID primary keys, foreign keys with sensible cascade behavior, uniqueness constraints for per-user progress, indexed foreign-key/status columns, and JSONB only for resources, options, rubric scores and answer payloads. RLS will be enabled on every table. Learners will never be granted access to `questions.correct_index` or `questions.explanation`; learner question reads will use the safe column grant and quiz submissions will call the security-definer RPC.

The admin email is applied during the auth-user profile trigger. The admin UI still checks the database role rather than trusting an email in the browser. Uploaded evidence remains in a private bucket under `<user-id>/...`, and the app creates short-lived signed URLs only after an authorized read.

External resources in the seed file will use stable sources such as MindTools, Toastmasters, Purdue OWL and Google Digital Garage where the exact URL can be verified. Any URL that cannot be verified will be marked `verified: false` and listed in `CONTENT_TODO.md`.

## Implementation sequence

1. Create the Vite/React project, dependency policy, route manifest and global design system.
2. Implement demo-mode repositories and authentication shell so the Preview is navigable without credentials.
3. Build public, learner and admin pages with reusable components and responsive states.
4. Add the ordered Supabase SQL schema, security policies, functions, storage policies and seed content.
5. Connect the Supabase repository path and `.env.example`, preserving demo fallback when variables are absent.
6. Run diagnostics, build checks and route/Preview inspection, then save the completed work as a checkpoint.
